Wallet abstraction: how it works

Manifest keeps fill proceeds in the trader's balance inside the market, and only the owner's signature can withdraw them. To send proceeds to the wallet "the moment it fills" without a custom on-chain program:

  1. A single wallet approval signs two transactions together:
    • the order: creates token accounts, wraps SOL, claims a seat, deposits exactly what the order locks, places it, and unwraps leftovers;
    • a claim: a durable-nonce transaction that withdraws the order's full-fill proceeds to the user's own wallet (unwrapping SOL).
  2. The keeper watches the market. Once the order has fully filled, it adds its fee-payer signature and submits the claim. The keeper can't change the transaction or send funds anywhere else.
  3. Cancel = cancel + withdraw everything + advance the nonce. That voids the unused claim and frees the nonce for the next order.
  4. A wallet's first order needs a one-time setup approval: two nonce accounts, refundable ~0.0029 SOL. Every order after that is a single approval.

Verified against the real Manifest program on a local validator (7 scenario tests plus a UI test using a mock wallet):

  • full fill pays out (sell and buy);
  • SOL proceeds arrive as native SOL;
  • partial fill then cancel returns everything, and the stale claim is rejected;
  • later orders take a single approval;
  • an order that fills instantly still pays out;
  • cancelling one order doesn't take another order's partial proceeds.

Bugs in Manifest's SDK that this work had to route around:

  • The SDK's core deposit/withdraw builders add a byte the program rejects, so those two instructions are hand-encoded.
  • The program no longer emits PlaceOrderLog. Sequence numbers are read from the batch-update return data instead.

Partial fills stay in the market until the order completes or is cancelled. The UI shows them, with a one-click withdraw.

Routing (next)

Today every resting order goes to the busiest Manifest market for the pair. Planned routing:

  • Market and marketable orders: take liquidity across order-book venues only, for example Jupiter's swap API restricted to dexes=Manifest,Archer (no AMMs).
  • Resting remainder: Manifest. It has no fees, and Jupiter routes through every order on the book.
  • Pairs with no Manifest market: offer to create one (~0.007 SOL).
  • Archer: route resting orders there only if our users' books can be added to its registry.

Open risks before launch

  • Real-wallet behaviour. Durable-nonce transactions signed via signAllTransactions passed with a mock wallet. Phantom, Solflare and Backpack each still need a small real order: do they warn, and do they keep the pre-signed nonce signature intact?
  • Keeper needs SOL (~0.00001 per claim). If it runs dry, claims wait and users fall back to withdrawing manually.
  • Global orders. Some Manifest liquidity is "global" (capital shared across markets) and may be unbacked at match time, so the book can overstate depth slightly.
  • Custody posture. The server stores pre-signed claims. A leaked claim can only ever pay its own user, but treat the store as sensitive anyway.
